# Subsystem: Reporting (General Report / overview / graphs / quick-stats)

Seeded from the OS backend mirror (`~/dev/gymstudio/backend`, TypeScript/Express/Sequelize) during
`analysis:mission-control` (2026-08-12, backend @ f74e8c5). Paths mirror-relative. Structure only.

This is the subsystem Mission Control composes over. The load-bearing fact: **every report is a
live query over event tables filtered by a date range — there is no stored snapshot / point-in-time
state anywhere.** Flow metrics reconstruct historically from immutable event timestamps; stock
(point-in-time) metrics do not.

## The composition surfaces that already exist

- `reports/routes/getOverview.ts` — `GET /overview`, gated `[OWNER, ADMIN]`. Composes
  `membersGetSummary + salesGetSummary + bookingsGetSummary` for a `{startDate,endDate}` range.
- `reports/routes/getGraphs.ts` — same shape, returns per-day series (`salesGetData + membersGetData
  + bookingsGetAttendance`).
- `reports/routes/teambuildr/quickStats.ts` — `GET /teambuildr/quick-stats`, **`apiKeyAuth:true` +
  `Studio.assertFindByReq(req, [])`** (any authenticated studio user; system-integration pattern).
  Composes newMembers + signIns + cancellations for **today only** (timezone-aware via
  `zonedTimeToUtc(startOfToday, studio.timeZone)`). This is the existing "compose several metrics for
  an external caller" precedent Mission Control should model on.

All are **single-studio** — scoped by the `blsm-studio-id` header through `Studio.assertFindByReq`.
There is **no all-studios / cross-customer aggregate endpoint.**

## The delta mechanism (why "week-over-week" already half-works)

`reports/helpers/dateRange.ts` filters `field BETWEEN gte AND lte`. `prevDateRange.ts` builds the
**immediately-preceding equal-length window** (`subDays(gte, N)`…`gte-1ms`). Every summary/data
helper runs the current and previous window and returns `{count/total, prevCount/prevTotal}`. So
period-over-period deltas are native — **but only for flow metrics that carry an event timestamp**
(`Account.createdAt`, `Sale.invoiceDate`, `Booking.startDate`). Deltas are recomputed from raw rows
at query time, not read from snapshots.

## Metric provenance (code-confirmed unless noted)

| Metric | How it's computed | Historical? | Grain |

| New Members | `Account.count` where `createdAt` in range, `isDeleted:false` (`membersGetSummary`) — **new Account rows, NOT new paid memberships** | yes (createdAt immutable) | studio COUNT, DB-side |
| Gross Revenue | `SUM(Sale.total)` where `matchSucceededSale` (`origin ∈ {contract,retail,invoice}`, `transactionStatus ∈ {succeeded,refund,paid}`) + `isBlossom:false`, by `invoiceDate` (`salesGetData/Summary`) | yes (invoiceDate immutable) | studio SUM, DB-side. Refund-status rows are summed in → gross-vs-net depends on sign of refund `total` |
| Client Visits / Sign-Ins | `Booking.count` where `isSignedIn`, `status=booked`, by `startDate` (`bookingsGetSummary`) | yes | studio COUNT |
| Cancellations | `Booking.count` where `status ∈ {canceled,late-cancel}`, by `startDate` | yes | studio COUNT |
| Active Members | **not in reports.** `accounts/routes/readMany.ts` filter: `ACTIVE_MEMBERS`=`isActive=1`; `ACTIVE_MEMBERSHIPS`=`isActive=1` + required active contract. Live list filter, current-state only | **no** (current state) | list, not a metric |
| ARM (avg value) | `contracts/routes/readMany.ts:230-250`: `revenue = Σ(contract.total / weeks(interval) * 4.3)`, `averageValue = revenue / activeMembershipCount`. **Contracted MRR, hardcoded 4.3-week fudge, not collected revenue.** Code comment admits owners complain the number's off | **no** (current active contracts) | in-memory over active contracts |
| # Sessions (classes/appts run) | **computed nowhere.** No `ScheduleItem.count` in reports | — | net-new |
| People / Session | — (needs sessions ÷ sign-ins) | — | net-new |
| Terminations | `Contract.endDate` + `isCanceled`/`hasEnded` flags. **No `canceledAt` timestamp, no churn/termination event table.** Queryable by `endDate` window but scheduled cancels are future-dated and cancels are reversible → mutable, not audit-grade history | partial/mutable | Contract rows |

| LTV | **zero code in backend.** Net-new modeling | no | net-new |

## Revenue ↔ payment processor

`Sale` (`sales/mysqlModel.ts`) is OS's **internal ledger**, not a Stripe mirror: it has a
`paymentProvider` field (`PaymentProvidersENUM.STRIPE` is one value among several), and rows are
generated by contract-billing crons (`crons/routes/contractCrons.ts:184`), retail import, studio
upgrades, and client checkout. So revenue does **not** strictly require Stripe — but it **does**
require OS to have recorded the transaction. Gyms collecting entirely outside OS have no `Sale` rows
→ revenue/ARM/LTV render empty or understated.
