# P14 — Vector memory layer design

**Date:** 2026-04-29  
**Status:** Draft, pending implementation

---

## Problem

The current memory system (P3) works in three steps: observe structured signals, synthesize them into markdown files with Claude, and retrieve them by recency into the brief prompt. It does the job, but it has a ceiling.

Retrieval is recency-based. `memory_retriever.py` loads `.md` files sorted by modification time and fills a 550-token budget. If the most relevant memory for today's brief was last updated 8 days ago but three other files were touched yesterday, the relevant one gets pushed out. There's no way to ask "what do I know about deals going cold?" — you get whatever fits chronologically.

Cross-source connection is impossible. The synthesizer groups observations by `entity` field (string match). A Slack message about "that gym in Baton Rouge" can't connect to a Gmail thread about "TGMC onboarding" or a calendar event with Patrick Labat's name on it. The relationship between these signals is semantic, and the current system only does string identity.

The Telegram query path (`processors/query.py`) has the same limitation. `_load_local_context` dumps raw pipeline JSON, people files, and memory files into the system prompt. For a question like "what's fallen through the cracks?" it sends everything and hopes Claude can sort it out within the context window.

**What this feature adds:**

1. Semantic retrieval — query by meaning, not by file recency
2. Cross-source pattern detection — signals from Gmail, Slack, Calendar, and Pipeline cluster by topic regardless of which API they came from
3. A foundation for proactive pattern surfacing — periodic clustering can identify emergent themes the synthesizer hasn't named yet

---

## Architecture

The vector layer sits alongside the existing file-based memory, not replacing it. Observations and synthesized memory files continue to exist as they do today. The vector store is a parallel index that makes them queryable by meaning.

```
Daily Run (existing flow — unchanged)
  ├── collect data → generate brief → send
  ├── memory_observer: append to observations.jsonl
  └── memory_synthesizer: Claude → update data/memory/*.md

Vector Layer (new — runs after observer and synthesizer)
  ├── vector_ingest: embed new observations + updated memory files → upsert to Pinecone
  ├── vector_retrieve: query Pinecone with today's context → return ranked chunks
  └── vector_retrieve replaces recency-based retriever in brief.py and query.py

Pinecone Index: "chief-of-staff"
  ├── namespace: "observations"  (raw signals — granular retrieval)
  └── namespace: "memories"      (synthesized .md files — high-level context)
```

Two namespaces in one index. Queries hit both namespaces and merge results. Raw observations give specificity ("Patrick Labat stale 40 days, In-Trial"). Synthesized memories give patterns ("Tzach Feinsilver reactivation flagged every day for a week, still not sent"). The brief prompt gets the best of both.

**Data flow:**

1. `memory_observer.py` appends to `observations.jsonl` (unchanged)
2. `memory_synthesizer.py` writes/updates `data/memory/*.md` (unchanged)
3. **New:** `vector_ingest.py` reads new observations since last ingest + any updated `.md` files → generates embeddings via Voyage AI (`voyage-3-lite`) → upserts raw vectors to Pinecone with metadata
4. **Modified:** `memory_retriever.py` queries Pinecone instead of reading `.md` files by recency. Query is built from today's calendar event names, email subjects, and open issue titles. Results are ranked by relevance, deduplicated, and trimmed to the token budget.
5. **Modified:** `query.py` uses the same vector retrieval for Telegram queries instead of dumping raw files.

**What stays file-based:**

- `observations.jsonl` — the append-only audit trail. Always the source of truth.
- `data/memory/*.md` — human-readable synthesized files. Still committed to git, still inspectable, still have TTL/expiry/pinned semantics.
- `data/state/` — daily snapshots, brief message IDs, etc.
- `pipeline_cache.json`, `issues.json`, `people/` — all unchanged.

The vector store is a derived index. If Pinecone goes down or the index gets corrupted, the system falls back to the current recency-based retriever. No data loss.

## Pinecone + Voyage AI specifics

- **Index name:** `chief-of-staff`
- **Cloud/region:** AWS us-east-1 (free tier default, closest to GitHub Actions runners)
- **Embedding model:** `voyage-3-lite` via Voyage AI API (matches existing OS assistant project)
- **Dimension:** 512
- **Metric:** Cosine
- **Namespaces:** `observations`, `memories`
- **Free tier budget:** 2GB storage, well under what this project needs (estimated ~2.5MB after a year of daily runs at 512 dims)

Embeddings are generated by calling the Voyage AI API separately, then upserted to Pinecone as raw vectors. This is the same pattern as the OS assistant project — Pinecone handles storage and retrieval, Voyage handles embedding.

**Vector metadata schema:**

For observations:
```json
{
  "date": "2026-04-29",
  "type": "pipeline_stale",
  "entity": "patrick-labat-tgmc",
  "source": "pipeline",
  "content_preview": "Patrick Labat — TGMC stale 40 days..."
}
```

For synthesized memories:
```json
{
  "topic": "pipeline-stale-post-demo",
  "last_updated": "2026-04-24",
  "expires": "2026-07-23",
  "pinned": false,
  "content_preview": "Tzach Feinsilver flagged every day..."
}
```

Metadata enables filtered queries: "show me only pipeline-related observations from the last 7 days" or "give me all memories that aren't expired."

## Embedding strategy

**Embedding pipeline:** Text → Voyage AI API (`voyage-3-lite`, 512 dims) → raw float vectors → Pinecone upsert. The Voyage call happens in `vector_ingest.py`, batching up to 128 texts per request (Voyage's batch limit). Voyage input type is `"document"` for ingest and `"query"` for retrieval (Voyage optimizes differently for each).

**What gets embedded:**

Raw observations — each JSONL line becomes one vector. The text to embed is `{type}: {content}` with `context` appended if present. This keeps embeddings focused on the signal content, not the metadata boilerplate.

Synthesized memories — each `.md` file becomes one vector. The text to embed is the content under `## Synthesized Memory`, stripped of the `_Last synthesized_` timestamp. If the file has a human-written section above the synthesized section, that gets prepended.

**What doesn't get embedded:**

- State snapshots, config, pipeline cache JSON, issues.json — these are structured data queried by key, not by meaning.
- People files — already matched by email address in the existing system. Could be added in a later phase.
- Draft files — ephemeral, generated fresh each day.

**Deduplication:**

Observations use `{date}:{type}:{entity}` as the vector ID. If the same entity appears in the same observation type on the same day (which happens — pipeline_stale entries repeat daily), only the latest upsert wins. This is fine because the content is nearly identical.

Memory files use `mem:{filename}` as the vector ID. When the synthesizer updates a file, the next ingest overwrites the old vector. This keeps the memory namespace current without accumulating stale versions.

**Ingest tracking:**

A small state file (`data/vector_ingest_state.json`) records the last-processed observation line number and the last-modified timestamps of memory files. Each run only processes new/changed data.

## Retrieval strategy

**For the morning brief:**

Build a query string from today's signals: concatenate calendar event summaries, email thread subjects (first 5), and open issue titles. Query both namespaces with `top_k=20`. Merge results, deduplicate by content similarity, and format the top results into the memory context string (capped at 550 tokens, same budget as today).

This replaces the recency-based file scan in `retrieve_memories()`. The function signature stays the same — callers don't know the retrieval method changed.

**For Telegram queries:**

The user's query text is the embedding query. Query both namespaces with `top_k=10`. Append the results to the system prompt as context, replacing the current `_load_local_context` dumps for memory and pipeline sections. Pipeline cache and people files are still loaded directly (they're structured data, not semantic).

**Fallback:**

If Pinecone is unreachable (network error, cold start timeout, rate limit), fall back to the existing file-based retriever. Log a warning. The brief still generates — just with recency-based context instead of semantic context. This makes the vector layer a progressive enhancement, not a hard dependency.

## Phased rollout

**Phase 1 — Embed observations at write time (this spec)**
- Add `pinecone` to requirements
- Create `processors/vector_ingest.py`
- Wire ingest into `main.py` after the observer/synthesizer calls
- Add `PINECONE_API_KEY` to GitHub Secrets and `.env`
- Add index creation script in `scripts/`
- No retrieval changes yet — just populating the index

**Phase 2 — Replace retriever with semantic search**
- Modify `memory_retriever.py` to query Pinecone
- Keep file-based fallback
- A/B test by comparing brief quality with recency vs. semantic retrieval
- Tune `top_k` and token budget

**Phase 3 — Semantic Telegram queries**
- Modify `query.py` to use vector retrieval for context
- Reduce raw file dumps in system prompt
- Measure token savings and response quality

**Phase 4 — Proactive pattern detection**
- Weekly job that runs clustering on the observation namespace
- Surfaces unnamed themes ("these 12 observations across 4 sources look like they're about the same thing but you haven't created a project for it")
- Feeds into weekly synthesis or surfaces as a Telegram alert

## Cost and limits

At current volume (~30 observations per day, ~15 memory files), the annual storage footprint is roughly:

- Observations: 365 days × 30 obs × 512 dims × 4 bytes = ~21 MB
- Memories: ~50 files × 512 dims × 4 bytes = ~0.1 MB
- Total: well under 100 MB after a full year

Pinecone free tier gives 2GB. This project will never touch the ceiling.

Voyage AI embedding costs: `voyage-3-lite` is priced at $0.02 per million tokens. Daily ingest is roughly 30 observations × ~50 tokens each = ~1,500 tokens/day. Annual cost: under $0.02. Effectively free.

Pinecone read/write units are included in the free tier at 2M write units and 1M read units per month. Daily usage: ~30 writes (observations) + ~15 writes (memories) + ~2 queries (brief + maybe Telegram) = nowhere near the limit.

## Risks

- **Cold start latency.** Pinecone serverless indexes sleep after 5-10 minutes of inactivity. The morning brief runs once daily, so the first query will hit a cold start (200-800ms). Acceptable — the brief already takes several seconds to generate.
- **Embedding quality on short text.** Some observations are terse ("Patrick Labat — TGMC stale 40 days"). `voyage-3-lite` handles short text well, but retrieval quality should be evaluated after Phase 1 data accumulates.
- **GitHub Actions network.** The Actions runner needs to reach Pinecone's API. Should work by default — Pinecone's API is a standard HTTPS endpoint, not a custom port.
- **Index deletion on free tier.** Pinecone archives free-tier indexes after 7 days of inactivity. The daily brief run keeps it active. But if the system is paused for a week (vacation, etc.), the index gets archived and needs recreation from `observations.jsonl`. The ingest script should handle this gracefully.
